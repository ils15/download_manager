# Independent Download Manager

An independent Windows desktop HTTP(S) download manager prototype. It uses a native Slint UI, a Rust transfer engine, and an optional Chrome Manifest V3 extension. No Internet Download Manager source, branding, artwork, assets, or proprietary algorithms are used.

## Implemented in this workspace

- Window layout follows the classic download-manager shell: a menu bar (Tarefas, Arquivo, Downloads, Visualizar, Ajuda, Registro), a toolbar of large icon+label buttons (Adicionar, Iniciar, Parar, Parar (todos), Excluir, Excluir (todos), Opções, Agendar, Iniciar fila, Parar fila, Grabber, Indique), a resizable category tree on the left, a virtualized download table on the right with a sticky column header (nome, tamanho, status, progresso, ETA, velocidade, prioridade), and a status bar with live counters, aggregate speed, and the details of the selected item. Adding a download, the transfer options, the history, and the about box are modal popups; the URL, destination, priority, segment limit, per-download speed cap, expected SHA-256, and the UTC scheduling window are validated in the dialog before the queue accepts the job. Toolbar and menu actions reflect the current selection and the real queue state, and every control is reachable by keyboard with a visible focus ring, an accessible name, and a live region for status and progress changes. Icons are original vector glyphs drawn in Slint; no third-party artwork, IDM assets, or branding are used. Grabber, the archive category, and product registration are not implemented and are shown disabled with an explicit “not supported” label instead of simulated behavior.

- Manual HTTP(S) URL entry and a queue with configurable per-instance concurrent-job count (1–8), priority scheduling, persisted shared application-level average byte-processing pacing in bytes/second (0 = unlimited), and a separate per-download cap in KB/s. New jobs default to Normal; the selected job can be set to Low, Normal, or High. When a transfer permit becomes available, waiting jobs are chosen High → Normal → Low, with FIFO order among equal priorities. Active downloads are non-preemptive, and scheduled jobs join permit ordering only after their UTC window opens. Priority and permits are per app instance, not shared across multiple processes. No aging is used: sustained High-priority arrivals can indefinitely defer Low-priority work. The shared pacing applies across concurrent downloads in one app instance and updates immediately; separate app instances are not coordinated. It is not a strict instantaneous wire-rate cap. Each active transfer may hold one 16 KiB reservation, so C active transfers may hold up to C × 16 KiB outstanding; the shared token bucket may hold another 16 KiB. Each transfer may also retain one yielded response chunk (size controlled by the transport); lower-level client/OS buffering is outside these bounds. Concurrency changes take effect after restart; the per-download cap applies to subsequently queued jobs. Queue entries expose pause, resume, cancel, actual bytes received, and per-job progress. ETA is approximate and shown only when a validated total and stable positive speed are available; chunked or unknown-length responses show bytes without ETA. Speed samples cover active transfer time; pausing freezes the estimate, including against late in-flight progress notifications, while resume resets its baseline and hides ETA until new stable samples are available. The internal estimate expires at four active seconds without a fresh sample; under normal polling, removal is shown on the next one-second UI refresh (scheduler delays may extend that). Accessible text remains available per job, with polite announcements on status changes and each 10% progress step rather than every refresh. Missing settings use normal defaults; unreadable, malformed, or invalid settings show a startup warning before defaults are used.
- Terminal queue entries are persisted automatically in a dedicated history directory under the per-user app-data location (LocalAppData on Windows), capped at 500. Records contain final status, destination basename only, bytes, available SHA-256, UTC finish time, and URL origin+path only; credentials, query parameters, fragments, and destination directories are not stored. “Clear history” is an explicit user action; it advances a persistent generation so downloads accepted before the clear cannot restore old entries when they later finish, while newly accepted downloads remain recordable.
- Completion and transfer-failure notifications appear in an accessible in-app live region and can be dismissed. No OS toast, notification service, or telemetry is used.
- Async HTTP(S) transfer, bounded retry/backoff for transient failures, cancellation/pause/resume queue APIs, configurable finite per-download byte and absolute-duration limits, and a no-overwrite output commit. The absolute deadline includes active transfer, pauses/resumes, retries, and automatic cleanup associated with that session; cleanup still pending at the deadline is surfaced rather than extending the transfer. Redirects are deliberately not followed.
- Conditional multi-segment HTTP(S) downloading is available only when configured above the conservative default of one segment. For files of at least 8 MiB, a bounded `bytes=0-0` probe must establish a valid `206`, exact one-byte `Content-Length`/`Content-Range`, total size within the byte cap, and a strong ETag. Up to four independently range-checked requests then require exact lengths, ranges, total, and the same ETag. Each segment writes to its own exclusively-created temporary file; verified files are concatenated in order into the normal staging handle. Temporary disk use can approach twice the final file size. Any unsupported or inconsistent range response deletes segment staging and falls back to a fresh single-stream request without touching the final destination. A range body that ends before its advertised length counts as inconsistent: the segmented attempt is abandoned, the segment staging is discarded, and the single-stream request decides the outcome. If that single-stream body is incomplete too, the transfer fails as a clean error, publishes no destination, and keeps only the in-process partial owned by the session for the explicit local cleanup. The configured total connection quota includes segment connections; shared global byte pacing, per-download speed cap, byte cap, and absolute deadline apply. Progress aggregates bytes written once and ETA uses the validated full size. Segment temp paths stay registered to the in-memory session so timeout cleanup retries them after worker cancellation. Segments are never resumed after restart; segmented partial state is not retained as a resume validator.
- A paused transfer can resume with `Range`/`If-Range` only while its exclusively-created partial file handle remains open in the running process. Completed writes retain their accounted offset on that handle for in-process resume; pause does not flush or promise crash-safe durability. The final commit syncs before linking. One absolute deadline is stored when a session first starts; pause time counts and resume does not renew it. Persistent/on-disk resume is intentionally disabled; after app exit, that transfer starts over rather than reopening an untrusted path. A forced process termination can leave an ignored random-name partial file behind.
- Optional expected SHA-256 validation in the transfer API and UI. An empty checksum field disables expected-hash checking; nonempty input must contain exactly 64 hexadecimal characters with no whitespace (uppercase hex is accepted). The reported digest is calculated from the staging-file handle; it is not a guarantee against a local writer racing the pathname-based hard-link commit. See `SECURITY.md`; adversarial consumers must re-hash the destination and/or isolate the directory.
- Optional daily UTC scheduling from the add-download form. The schedule toggle defaults off and enabled windows require valid 24-hour `HH:MM` values; equal bounds mean all day and overnight windows are supported. The queue rechecks the window after resource waits and releases its transfer lock/permit before waiting for the next daily occurrence. Closed windows are polled every 30 seconds, so an opening may be noticed up to roughly 30 seconds late, before any additional resource wait. Windows local time is not used, avoiding ambiguous DST behavior.
- Chrome MV3 popup with `activeTab` and `nativeMessaging` only. It reads the active tab URL after a deliberate button click and sends only `{ action, url }`; it never reads page contents, cookies, credentials, or browser session state. Common auth-like query keys are rejected in both extension and native host.
- Inno Setup script defaults to per-user installation. The installer can present the standard all-users privilege override, which is where Windows UAC is requested. The application itself never elevates or accesses the registry.
- Windows x64 GitHub Actions runs on `windows-2025`, disables persisted checkout credentials, pins actions by SHA, and is configured for formatting, Clippy, locked tests, and release builds on Rust 1.92.0 (declared MSRV) and 1.99.1. Only the Rust 1.99.1 matrix leg downloads Inno Setup 7.1.0 from its official release URL, verifies the SHA-256, compiles `installer.iss`, and uploads `setup-independent-download-manager.exe` as a template artifact. The template is not functional while its placeholder extension ID remains: installation must use an explicit valid Chrome ID, either an unpacked development extension ID or a future Store ID; a Web Store ID is not strictly required. The workflow is configured but has not yet been executed, so Windows builds/tests and the installer artifact remain unverified. Actions artifacts are not releases, and no Release or Store publication occurs. `Cargo.lock` is Cargo-generated; dependency review remains pending.

## Chrome setup

The CI installer artifact is a template. Enter an explicit valid Chrome extension ID in its installer page to generate the allowed-origin entry and register the host. For unpacked development, if the ID is not yet known, install once with the field blank, load `{app}\extension` as an unpacked extension, read its ID from `chrome://extensions`, then rerun the installer with the same user/machine mode and installation path and enter that ID. The blank-ID install writes a placeholder and cannot connect until replaced by an explicit ID. An unpacked development ID is sufficient; a future Store ID may also be used, but Web Store publication is not required. For unpacked extensions, use the ID from the installed `{app}\extension` directory. The installer owns the normal Chrome Native Messaging registry registration; the app and extension do not modify registry state. The host accepts only an explicit HTTP(S) URL request and places it in the app's one-shot local inbox. A running app polls the inbox; otherwise it is consumed at the next app start.

No fixed extension key or signed extension is included. The installer template itself is not a usable Native Messaging setup until an explicit extension ID replaces the placeholder.

## Security and behavior boundaries

- The HTTP client has no cookie jar, browser integration, credential extraction, authentication support, or DRM/access-control bypass. URL userinfo and common authentication-like query keys (tokens, signatures, API keys, sessions) are rejected; ordinary query parameters remain allowed. The Native Messaging payload rejects unknown fields.
- In-process resume is tied to a SHA-256 fingerprint of the exact URL, a strong ETag, and the byte offset held by the open file session; no resume metadata or raw URL is persisted. A range response must match the requested start, complete end/total, validator, and exact response-body length. A server that does not provide a strong ETag can still be downloaded, but cannot be safely resumed.
- Redirects are not followed, including same-origin redirects. This is intentionally conservative and may make some download URLs unsupported.
- SHA-256 validation covers bytes read from the open staging handle. A process with write permission to the destination directory may replace the staging pathname between hashing and the hard-link commit, so the final destination is not guaranteed against that local TOCTOU attacker. Consumers requiring adversarial integrity must re-hash the destination and/or use external isolation.
- URL selection is explicit; manually supplied URLs can still refer to private/local HTTP services. Users should only submit trusted URLs. No crawler/site-grabber is implemented.
- Downloads go to the user's `Downloads` directory. Output names are reduced to a sanitized leaf; an existing final file is not overwritten. The default maximum is 4096 MiB per download and 360 minutes total; both are configurable in the Transfer limits panel (within validated finite ranges). Each response chunk is checked against the aggregate cap before writing, including chunked bodies without `Content-Length`.
- No telemetry is included. The URL field is manual; its standard `LineEdit` accepts explicit Ctrl+V pasting only after that user gesture. The app does not monitor or read the clipboard automatically. Settings and history are written to unique same-directory `create_new` temporaries, `sync_all`'d, then atomically replaced (rename on Unix, `ReplaceFileW` on Windows when a file already exists). A replacement failure before commit leaves the prior file intact, and atomic replacement protects against partial file contents in ordinary failure cases. The parent directory is not fsync'd on every platform/filesystem, so the most recent save—including a history clear-generation update—may be lost after abrupt power loss; crash-safe durability is not promised. History read-modify-write, enqueue-generation capture, and clear operations use a per-user interprocess file lock and reload/sanitize/cap the current file before updating it. Legacy history is removed only after a valid replacement is written and verified; if both current and legacy files are malformed, startup reports an error and preserves their original bytes for recovery. Unix history directories are mode 0700 and history data, lock, and temporary files are mode 0600. On Windows history remains under LocalAppData; its ACL is inherited from the user-profile directory and has not been explicitly verified. Concurrent settings saves remain atomic last-writer-wins, not merged.
- Native Messaging producers write a unique `incoming/*.tmp`, sync it, then atomically rename it to `*.json`; the poller ignores temporary files. Interrupted temporaries are not consumed. Recover a `.tmp` only after confirming its producer has finished and no instance is still writing it; never rename a live temporary. Then inspect it, remove it if incomplete, or rename a verified complete message to `.json` to retry.
- Polling is single-flight within each app instance, and an exclusive per-item claim marker (`incoming/.<item>.claim`, created with an atomic exclusive create) decides which consumer owns an inbox URL, so concurrent consumers cannot queue the same URL twice. The winner moves the item into an opaque `.processing-<id>` folder and releases the marker; a consumer that loses the marker skips the item without an error, and a failed rename releases the marker so the item stays claimable. A marker left behind by a crashed consumer is treated as crash residue and recovered after a ten-minute threshold, with one recovery attempt per item and poll cycle. A claim remains in the folder until queue acceptance; enqueue failure restores it to `incoming`, while failed restoration leaves the claim and displays its recovery path. A destination duplicate is acknowledged only for an exact URL/destination match in Queued, Scheduled, Downloading, Paused, or Completed state. Cancelled and FailedCleanupPending jobs do not qualify; Failed jobs are eligible for a normal enqueue attempt.
- Malformed, unsupported, oversized, or policy-rejected inbox items are moved intact to `rejected/` under opaque names, with generic diagnostics that omit message contents and source filenames. Review them manually; only after confirming a valid, intended request should a user resubmit it through the explicit extension action or move a corrected message to a fresh `incoming/<new-id>.json` name. A crash around queue acceptance is ambiguous and claims are not automatically replayed. After stopping all app instances, inspect queue/output state before manually moving a retained processing `message.json` to a fresh `incoming/<new-id>.json` name; manual recovery can cause a duplicate download. Query/fragment values are omitted from the visible queue URL.

## Not implemented / requires follow-up review

- No site-grabber (not implemented; public-address, redirect/DNS-rebinding, page/depth/byte limits are absent); no FTP or MMS transport (not implemented or compatibility-reviewed); no antivirus integration (not implemented; reviewed vendor/OS integration and packaging would be required); no OS desktop notifications or global cross-instance coordination for priority or aggregate bandwidth. Per-instance priority scheduling is implemented as described above. ETA is a rough active-transfer estimate, not a completion guarantee; it requires repeated positive samples over at least two seconds and a known validated response total. Its internal cutoff is four active seconds without a fresh sample; under normal polling, removal appears on the next one-second refresh (scheduler delays may extend that).
- Persistent resume metadata is not written; single-stream pause/resume remains process-local and tied to an already-open handle. Segmented transfers are deliberately not resumed by segment after a pause, failure, or restart; a later single-stream attempt starts over.
- If final output is committed but deletion of its temporary alias fails, the job is still reported Completed with an explicit cleanup-pending diagnostic; cancellation cleanup failures similarly remain visible. The UI enables “Retry pending cleanup” for these states and reports the retry result; queue/API callers can also use `DownloadQueue::retry_cleanup`. This explicit retry only removes the owned temporary file alias and updates local session state: it performs no network request and may be used after the transfer deadline. The session handle/path remains owned until removal succeeds.
- The Windows workflow is configured to compile and upload an Inno Setup template only in the Rust 1.99.1 matrix leg; it has not yet been executed. The artifact remains nonfunctional until installation uses an explicit Chrome extension ID. Windows execution/build/test, inherited ACLs, Native Messaging registration, uninstall behavior, Slint/UI, Inno Setup privilege behavior, Windows path/atomic-file behavior, and dependency resolution still require Windows review.
