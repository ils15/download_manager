# Security notes and review checklist

- Clean-room implementation; no third-party download-manager code or assets are incorporated.
- The repository does not yet include a `LICENSE` file. No license is granted until the project owner explicitly chooses one; do not add a license header, a `LICENSE` file, or a copyright notice on the owner's behalf.
- Network requests are limited to absolute HTTP(S) URLs without userinfo or common authentication-like query keys. The HTTP client uses Rustls, has no cookie store, and disables redirects. No authentication headers are created.
- Chrome integration has no content script or broad host permission. `activeTab` access is exercised only after the popup button click. Native messages have a 1 MiB cap and a strict `{ "action": "download", "url": "..." }` schema; extra properties are rejected.
- Queue controls act on a specific job ID and are dispatched asynchronously; UI updates return through Slint's event loop. The add form validates an optional expected SHA-256 before enqueueing and only schedules when the user enables a daily UTC window with valid `HH:MM` bounds. Per-job progress uses bytes actually written and remains available as text. ETA is approximate, requires repeated positive samples spanning at least two seconds and a known validated total, and is omitted for unknown/chunked lengths; the internal active-time expiry is four seconds, with removal shown on the next one-second UI refresh under normal scheduling (delays may extend it). Sampling excludes pauses; paused estimates remain frozen even if an in-flight write reports completion after pause, and resume clears the prior speed baseline until fresh samples stabilize. A polite textual live region announces state changes and 10% progress steps, not every refresh; no progress-indicator role is claimed because the UI has no graphical progress bar. ETA and monotonic clock values are runtime-only and are not stored in history; history timestamps continue to use explicit UTC `SystemTime` formatting.
- Priority scheduling is per app instance: whenever a transfer permit becomes available, waiting jobs are selected High → Normal → Low, with FIFO order within each priority. Active downloads are non-preemptive. No aging is used, so sustained High-priority arrivals can indefinitely defer Low-priority jobs; there is no global cross-instance priority coordination.
- Terminal history is stored in a dedicated per-user history directory (LocalAppData on Windows), with at most 500 entries. It stores status, destination basename only, bytes, available SHA-256, and a UTC timestamp; destination directories are not persisted. URLs are reduced to origin+path (no userinfo, query, or fragment), and failure detail strings are not persisted. Recording is automatic; clearing is an explicit in-app user action. Every load, append, enqueue-generation capture, and clear uses an exclusive `File::lock` lock file and reloads the current on-disk data. Jobs capture the persisted generation when accepted; clear advances it under the lock, so a completion from an older generation is ignored and cannot repopulate cleared history. Writes use an exclusive same-directory temporary with `sync_all`, atomic replacement, and read-back verification. The temp file is synced before replacement, but the parent directory is not fsync'd on every platform/filesystem; replacement protects against partial file contents in ordinary failure cases, not against loss of the latest write or clear-generation update after abrupt power loss. Crash-safe durability is not promised. Corrupt current data is recovered from valid legacy data; if existing current/legacy data is malformed and neither provides a valid document, startup returns an error without changing the original file bytes. A legacy file is removed only after valid current data is confirmed. On Unix the directory is mode 0700 and data, lock, and temporary files are mode 0600. On Windows ACLs are inherited from the LocalAppData/user-profile directory and have not been explicitly verified.
- Completion and transfer-failure notifications use a dismissible Slint in-app live region. They do not use OS toast APIs, external notification services, or telemetry.
- The URL field accepts an explicit Ctrl+V paste through its standard `LineEdit`; clipboard access occurs only on that user gesture. There is no clipboard listener, monitoring, or automatic read.
- Native Messaging producers write and sync a unique `incoming/*.tmp` before atomically publishing it as `*.json`; pollers ignore `.tmp` files. Recover a temporary only after confirming its producer has finished and no instance is still writing it; never rename a live temporary. Then inspect it, remove it if incomplete, or publish a verified complete message by renaming it to `.json`. Per-item ownership is decided by an exclusive claim marker `incoming/.<item>.claim`, created with an exclusive `create_new` open (`O_CREAT|O_EXCL` on Unix, `CREATE_NEW` on Windows), so exactly one consumer can hold an item even when several race. A same-volume rename alone cannot decide this on Windows, where `MoveFileExW` lets two concurrent consumers move the same source and therefore queue the same URL twice. A consumer that loses the marker skips the item without an error. The winner moves the item with a same-volume rename into an opaque `.processing-<id>` folder and then removes the marker; the marker is removed only while it still carries that claim's own token, so a consumer never releases a marker another consumer has taken. The content remains in the claim folder until queue acceptance is acknowledged. Enqueue failures restore the item; failed restoration keeps the claim and reports its recovery path. A failed rename releases the marker, inspects the source exactly once (a source that is still there is a genuine failure, reported with the item untouched; a source that disappeared proves another consumer won), and never leaves an orphan marker behind. A marker older than ten minutes is treated as crash residue: it is removed and the claim is retried once per item and poll cycle, so two consumers cannot loop against each other; a marker with an unknown or future modification time is never treated as stale. The post-rename token check refuses to queue a copy whose marker was taken by a stale-marker recovery, so a consumer that stalled for longer than the threshold cannot queue the same URL twice. On Unix the marker is mode 0600; on Windows its ACL is inherited from the per-user app-data directory and has not been explicitly verified. A marker whose item no longer exists is inert and can be deleted manually. A destination duplicate is acknowledged only when snapshots prove exact URL/destination and the existing job is Queued, Scheduled, Downloading, Paused, or Completed. Cancelled and FailedCleanupPending do not qualify; Failed remains eligible for a normal enqueue attempt.
- Malformed, unsupported, oversized, and policy-rejected messages are moved intact to `rejected/` under opaque names; diagnostics expose only a generic reason and opaque quarantine path, never message contents, URL values, or source filenames. Review quarantined content manually; only a verified intended request should be resubmitted through the explicit extension action or moved as a corrected message to a fresh `incoming/<new-id>.json` name. A crash around queue acceptance is ambiguous, so processing claims are not automatically replayed. After stopping all app instances, inspect queue/output state before manually moving a retained `message.json` to a fresh `incoming/<new-id>.json` name; manual recovery may repeat a download.
- Settings are written to a unique same-directory `create_new` temporary and synced before atomic replacement (rename on Unix, `ReplaceFileW` on Windows when a file already exists). Replacement failures do not delete the old settings file; the directory-entry durability caveat above applies. Cross-instance saves are atomic last-writer-wins, not a merge: a stale settings snapshot can overwrite newer values.
- SHA-256 is calculated over bytes read from the open staging-file handle. The commit then creates the final hard link using the staging pathname. A concurrent process with write access to the destination directory can replace that staging alias between hashing and linking, causing the destination to differ from the bytes whose hash was calculated. This same-user/local-writer race is outside the integrity guarantee and trust boundary; neither the displayed digest nor expected-hash validation guarantees the final destination against local tampering. Consumers requiring adversarial integrity must re-hash the destination and/or isolate the destination and staging directory from untrusted local writers.
- Single-stream partials use an unpredictable same-directory name and exclusive `create_new` creation. The open file handle stays in the queue entry and is never reopened by path; range resume is process-local and requires a matching strong ETag plus strict start/end/total/Content-Length/body-length checks. Completed writes update the in-memory offset and remain available through that handle on pause; pause does not flush and is not crash-safe durability. Conditional multi-segment mode defaults to one segment and is capped at four. It requires a `206` probe with exact one-byte `Content-Length`, exact `Content-Range`, a total within the configured byte cap, and a strong ETag. Every segment must return the exact requested range, total, body length, and unchanged ETag. Segments write to separate same-directory exclusive temporaries, are concatenated in range order into the ordinary staging handle, and are removed before the final hard-link commit. On unsupported or inconsistent range behavior, all segment temporaries are cleaned and a new single-stream request is used; the final destination is never replaced. A range body that ends before its advertised length counts as an inconsistent range response: the segmented attempt is abandoned, the segment staging is discarded, and the single-stream request decides the outcome. An incomplete single-stream body fails as a clean transfer error, publishes no destination, and leaves only the in-process partial owned by the session for the explicit local cleanup. Segmented bytes are not resumable; no segment metadata is persisted. Temp paths remain registered in the in-memory session for post-cancellation/timeout cleanup. Cancellation/deadline drops close owned handles before best-effort same-directory removal, and explicit cleanup failures are surfaced.
- If post-commit alias deletion fails, the final download remains Completed with `cleanup_pending` diagnostics rather than becoming Failed; the queue retains the session until cleanup succeeds. Discard/cancel failures retain the open handle and path, return an error, and expose a cleanup-pending state; the UI retry action and `DownloadQueue::retry_cleanup` retry removal, updating the diagnostic only after removal succeeds. That explicit retry is local filesystem/session cleanup only (removing the owned temporary alias); it performs no HTTP or other network operation and remains available after the transfer deadline. Do not treat an error return as successful cleanup.
- Every request has a finite configurable byte cap (default 4096 MiB per download) and an absolute transfer deadline (default 360 minutes). The byte cap is checked before every body write even when the response is chunked or omits `Content-Length`; segmented mode also rejects totals above that cap before requesting segments. Separately, a persisted shared application-level average byte-processing pacer is attached to each process-local `DownloadQueue`: it aggregates every segment and concurrent transfer in that instance and 0 means unlimited. It reserves one bounded quantum before polling each next response chunk and processes larger yielded chunks in bounded subparts. At most one 16 KiB reservation is outstanding per active HTTP stream, so the instance-wide configured connection quota bounds total outstanding reservations; the shared token bucket may also hold up to 16 KiB. Each active stream may additionally retain one transport-sized yielded chunk, and HTTP-client/OS internal buffering is outside these bounds. This is not a strict instantaneous wire-rate cap. Distinct app instances have distinct pacers and are not coordinated. Missing settings use defaults normally; unreadable, malformed, or invalid settings cause a startup UI warning before defaults are used. The absolute deadline covers the transfer session, including pauses/resumes and automatic cleanup associated with the session; automatic cleanup that cannot finish within the deadline remains `cleanup_pending` for the explicit local retry described above.
- App-data inbox/settings/history are per-user. History is kept under LocalAppData on Windows; its ACL is inherited and has not been explicitly verified. The app itself does not write registry entries, elevate, or invoke PowerShell/shell commands. Inno Setup's standard Native Messaging registration uses the selected user/machine hive and its optional all-users mode is the only UAC path.
- Native Messaging's allowed origin is configured by the installer's extension-ID field; leaving it blank writes an unusable placeholder, which must not be replaced with a wildcard. The Windows CI installer artifact is only a template and is not functional until an explicit valid Chrome extension ID is entered. That ID may belong to an unpacked development extension or a future Store extension; Web Store publication is not required. Do not distribute an unpacked extension or installer until this flow and installer registry behavior have been reviewed on Windows.
- Focused local loopback tests were added for range ordering/content/hash, unsupported-range fallback, changed validators/range rejection, truncated segment fallback, an incomplete single-stream body in that fallback, cancellation/deadline temporary cleanup, and shared global byte pacing. They have not been executed. The total connection quota is per queue instance and caps simultaneous segments plus other active transfer streams; separate instances remain uncoordinated.
- Segmented assembly temporarily stores the segment files and a second full staging file, so local disk usage can approach twice the configured final download size; a full disk fails safely before the destination commit and invokes temporary cleanup.
- Residual risks: DNS resolution/private-network destinations are not blocked for manually selected URLs; redirects are unsupported; the one-shot Native Messaging inbox temporarily stores the explicitly opted-in URL; history is intentionally capped and is not a full audit log; malicious same-user filesystem interference and filesystem filters are not fully defended. Do not submit authenticated/signed URLs or URL-embedded secrets. Site-grabber, FTP, MMS, and antivirus integration are explicitly out of scope and unimplemented. Any future site-grabber must add public-address and same-origin checks, strict page/byte/depth limits, and redirect/DNS-rebinding review before implementation.

## Windows review gates

A previous verification run reported `cargo fmt --check`, `cargo test --locked --all-targets` (98 passed), `cargo clippy --all-targets --locked -- -D warnings`, and `cargo build --locked --release` as **PASS** on WSL2 Linux x86_64 with rustc/cargo 1.99.0. Coverage is **NOT MEASURED**. These results come from a previous verification run and were not independently executed or verified in this review; they do not establish Windows/MSVC or Windows 10 x64 compatibility. That run predates the segmented-transfer work and the single-stream fallback correction and has not been re-executed since, so the 98-test figure is stale, the current test count is unknown, and no new count is claimed as verified.

Before distribution, review the Cargo-generated `Cargo.lock` graph and execute the configured Windows workflow on a clean Windows 10 x64 environment. Its Rust 1.92.0/1.99.1 matrix runs formatting, Clippy, locked tests, and release builds. Only the 1.99.1 matrix leg downloads Inno Setup 7.1.0 from its official release URL, verifies its SHA-256, compiles `installer.iss`, and uploads the resulting installer template artifact. The workflow is configured but has not yet been executed; therefore the matrix, Windows/MSVC execution/build/test results, and installer output are unverified. The inbox claim-marker change (exclusive marker, stale-marker recovery, and the concurrent-claimer tests) was written without running any command: it has not been compiled, formatted, linted, or executed, and the Windows-only double-claim stress test is validated only by the Windows CI job or a local Windows build. The template is not functional until an explicit valid extension ID replaces the placeholder; an unpacked development ID is sufficient, and a future Store ID is optional rather than a Web Store prerequisite. Actions artifacts are not releases, and no Release or Store publishing has occurred. Still review Slint UI behavior; range/validator and resource-limit behavior against a controlled local HTTP server; exclusive temp-file, interprocess history lock, and hard-link destination semantics on NTFS; inherited LocalAppData ACLs; Chrome Native Messaging framing and origin registration on Windows; per-user default and all-users UAC override; uninstall behavior; installer signing policy; dependency audit; and secret scan. CI disables persisted checkout credentials and pins its actions; these review items and all Windows gates remain pending. Do not push until controlled validation is complete.
